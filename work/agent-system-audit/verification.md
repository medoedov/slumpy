## 0. Главное

Система построена грамотно по замыслу: короткий постоянный контекст, права решений, один ревьюер со строгими критериями находки, решения и ловушки на диске, замеры с сырыми данными. Документация Claude Code использована верно: поля скиллов и агента, загрузка правила по путям и синтаксис разрешений соответствуют текущим страницам. Сырые данные замеров честно сохранены, и все итоговые суммы из них воспроизводятся.

Проблемы сосредоточены в трёх местах: защита от ошибочных действий слабее, чем записано; выводы замеров местами сильнее данных; процесс тяжелее, чем нужно, и при этом главные его шаги держатся на дисциплине модели.

**Серьёзные находки:**

| № | Находка | Серьёзность |
|---|---|---|
| A | Ветка GitHub по умолчанию `main` содержит старую систему с ложными фактами (Expo, Windows, старый CLAUDE.md). Облачная сессия, открытая без явной ветки, работает по ним. Запрет push в `main` обходится четырьмя проверенными формами команды, не касается инструментов GitHub MCP и при этом запрещает законный `git push -u origin HEAD` | Высокая |
| B | Рост цены от ревьюера занижен. В `baseline.md` +61% для ловушек и +140% для проектирования. На одинаковых случаях: +112% и +120%, по отдельным случаям с ревьюером от +58% до +289%. По правилу принятия из плана обязательный ревьюер на T1 должен стать кандидатом на снятие, а в отчёте он помечен как «не проверен» | Высокая |
| C | Прирост в продуктовых вопросах частично создан самим замером. Замер однотуровый, а скилл задаёт вопросы по одному. Все 6 ответов «после» содержат ровно один вопрос, поэтому критерии «не больше пяти» и «рекомендация у каждого» проверены на одном вопросе. По главной двусмысленности новая система хуже голой модели: 4 из 6 против 6 из 6. «Дешевле на 35%» относится только к первому вопросу; цена всего процесса спецификации не измерялась | Высокая для выводов |
| D | Уровень T2 назначается по области изменения. Почти каждая фича Slumpy трогает хранимые данные и данные пользователя, поэтому почти всё становится T2: бриф с двумя альтернативами, ADR, ревью решения, ревью кода, проход безопасности. | Команда | Ожидание по документации | Результат |
|---|---|---|
| `cd <tmp> && git push origin main` | Запрет | Запрещено |

**Вывод.** Правило ловит самую частую форму и мешает одной законной. Форма `git push -f` после перебазирования ветки, отслеживающей `main`, для агента естественна, и она проходит. Кроме того, правила касаются только Bash. Инструменты GitHub MCP в облачных сессиях (`push_files`, `create_or_update_file` с веткой `main`, `merge_pull_request`) ими не покрываются. Это вывод по синтаксису правил; вызовом я не проверял, потому что это запись в настоящий репозиторий.

**Ветка по умолчанию.** Проверено: в `origin/main` один коммит a45c5b4 со старым CLAUDE.md («Always use context7…», продукт как «partially agreed») и Project Knowledge под Expo. **Минимальное исправление.** Это внешние действия, они за владельцем. В настройках GitHub сменить ветку по умолчанию на `dev` и включить правило защиты `main` (ruleset: запрет прямого push и force-push, слияние только через PR). Около 10 минут, защищает от всех форм команды и от MCP. Правило `Bash(git push * HEAD)` убрать.

## 6. Замеры

### 6.1 Опираются ли выводы на сырые данные

**Да, по суммам и счётам.** Проверено:

- `summarize.py` по `evals/results/baseline/*` воспроизводит `evals/results/baseline/summary.md` дословно, отличаются только пути в первой строке.
- `compare.py` по тем же папкам воспроизводит все счёты таблиц 10.1 и 10.2 `baseline.md`.
- Суммы: замер «до» 27,73 USD по агрегатам плюс 0,88 USD пробных запусков дают 28,60 USD; замер «после» 21,57 USD плюс досъёмка «до» 3,91 USD дают 25,48 USD. Совпадает с `baseline.md`.
- Утверждения о ревьюере подтверждаются трассами: 8 запусков `reviewer` на 11 прогонов ловушек, по одному в D2 и D3, ни одного в R1–R9.
- Ручная проверка T1 и описание S3 соответствуют сохранённым ответам.

### 6.2 Где выводы сильнее данных

**1. Рост цены посчитан на разном наборе прогонов. Высокая.**

`compare.py` делит общую стоимость группы на число прогонов. В «до» среди 13 прогонов ловушек 5 прогонов T5, самого дорогого случая, а в «после» среди 11 прогонов только 2 T5. Средняя «до» завышена составом, поэтому рост выглядит меньше.

Пересчёт по одинаковым случаям, среднее по случаям, агент плюс оценщик:

| Группа | До | После | Изменение | Голая модель | После против голой |
|---|---|---|---|---|---|
| Ловушки T1–T5 | 0,689 | 1,463 | **+112%** (в отчёте +61%) | 0,598 | +145% |
| Проектирование D1–D3 | 0,361 | 0,794 | **+120%** (в отчёте +140% на D1–D4 против D1–D3) | 0,434 | +83% |
| Ревью R1–R9 | 0,305 | 0,218 | −28% | 0,255 | −14% |
| Продукт P1–P3 | 0,519 | 0,336 | −35% | 0,396 | −15% |

По отдельным случаям, где запускался ревьюер: T1 +283%, T2 +289%, T4 +58%, T5 +64%, D2 +214%, D3 +176%. Где ревьюера не было, цена упала: T3 −32%, D1 −3%. Связь роста цены с ревьюером подтверждается, а сам рост примерно вдвое больше записанного для ловушек.

Минимальное исправление: в `compare.py` считать среднее по случаям, присутствующим в обеих сторонах, и исправить цифры в `baseline.md`, раздел 8 и 10.2.

**2. Правило принятия к ревьюеру не применено. Высокая.**

План, раздел 9: механизм остаётся, если корректность не хуже, а рост цены не больше 25%. Механизм с нулевой разницей удаляется. Задание сессии Б: «Механизм без пользы пометь кандидатом на удаление». По данным ревьюер на T1 и T2 дал рост цены выше порога и не дал измеримой пользы. В таблице раздела 11 `baseline.md` он записан как «не проверен до сквозных задач на Mac». Заголовок 10.2 «не хуже и не дороже чем на 25%» противоречит содержанию таблицы под ним. Честная запись: «по правилу принятия не проходит; обязательность на T1 — кандидат на снятие; окончательно решит пилот на Mac».

**3. Продуктовый прирост частично создан форматом замера. Высокая для вывода, механизм при этом полезен.**

Проверено по `runs.jsonl`: все 6 ответов «после» на P1–P3 заканчиваются одним вопросом и словами «Какой вариант выбираете?» или обещанием следующих вопросов. Замер однотуровый. Поэтому:

- «не больше пяти вопросов, 6 из 6» на деле означает «один вопрос»; соблюдение лимита на всём диалоге не измерено;
- «рекомендация у каждого вопроса, 6 из 6» проверена на одном вопросе. Сам формат вопроса (суть, почему важно, варианты, рекомендация, что увидит пользователь) действительно лучше, это видно по ответам;
- по главной двусмысленности «после» 4 из 6 против 6 из 6 у голой модели. В `baseline.md` это сравнивается только с вариантом «до»;
- «дешевле на 35%» — цена первого вопроса. Полный процесс включает ещё 2–4 вопроса, запись `spec.md` и прогон ревьюера в режиме spec. Его цена не измерялась.

Минимальное исправление: переписать вывод как «формат вопросов улучшился; лимит пяти вопросов и цена процесса не измерены» и добавить многотуровый случай с листом ответов, как в разделе 9 плана для сквозных задач.

**4. Измерена не та версия системы, что внедрена. Средняя.**

`SOURCE` в папках «после»: коммиты c61a8cc и 9090c30. После них в CLAUDE.md добавлены разделы Scope, правила кругов, маршрут находок в `backlog.md`; в `reviewer.md` +26 строк: старые ошибки, класс находки, «пересмотреть подход». Ни одно из этих правил не измерялось. В `baseline.md` это не отмечено: заголовок говорит «коммит c61a8cc и позже».

**5. Уже записанные ограничения.** Мало повторов, насыщенные случаи, разный состав вариантов «до» и «после», оценщик — модель. Эти оговорки в `baseline.md` есть, и они честные.

### 6.3 Мелкие расхождения

- `baseline.md`, раздел 8: «агент сам назвал правку уровнем T2» в обоих прогонах S3. Проверено: метка «T2» есть в одном ответе, во втором написано «высшему уровню риска». По сути верно.
- Плечо «без системы» снято на Claude Code 2.1.310, «после» на 2.1.311. Влияние, вероятно, малое; в отчёте это упомянуто.
- Трассы прогонов удаляются скриптом `collect.py`, в репозитории остаются только итоговые ответы и вердикты. Поэтому путь агента (что он прочитал, какие вопросы задал ревьюеру) задним числом не проверить. Для следующих замеров стоит сохранять хотя бы трассы прогонов с перевернувшимися случаями.

### 6.4 Честность в целом

Оценка: данные честные, оговорки в основном честные, итоговые формулировки в двух местах сильнее данных: «большой прирост» по продуктовым вопросам и цена ревьюера. Ни одна цифра не выдумана; ошибки методические. Правило принятия как текст хорошее, но к самому дорогому механизму применено мягко.

## 7. Качество по существу

Оценка по восьми приоритетам. «Закрывает» означает, что есть механизм, который срабатывает без напоминания и чей эффект виден.

Ревью решения на T2 | Слабо на практике, хорошо на бумаге | Скилл загрузился в 3 из 16 прогонов «после», где он был нужен (D1, D3, один прогон T2; всего проектирование, ловушки и S3). В T1, T3, T4, T5, S3 его не было. Когда он срабатывает, бриф хороший |

Два прогона, где оценщик нашёл лишние слои, оба прошли через ревьюера. Это два случая из шести, доказательством не считаю |

### 7.1 Что сильный senior iOS-инженер сделал бы иначе

Оценки, не проверенные замером.

1. **Защиту `main` поставил бы на сервере.** Правило в GitHub ловит любую форму команды и любой инструмент. Клиентский список запретов он считал бы удобством для агента. Документация Claude Code прямо пишет, что такие правила не граница безопасности.
2. **Уровень риска привязал бы к принимаемому решению.** Новое хранилище, новая сущность с нестандартной миграцией, новое расширение, новый entitlement, новая зависимость — T2 с ADR. Необязательное поле с лёгкой миграцией и тестом на старых данных — T1. ADR пишется только тогда, когда принимается новое решение.
3. **Ревью назначал бы по сигналу риска.** Свежий ревьюер — на T2 и на изменения общего состояния и многопоточности. На остальное — компилятор, тесты, перечитывание собственного диффа. Это соответствует и правилу принятия из плана.
4. **Ставил бы напоминание в момент действия.** Хук перед правкой `.swift`-файла в чувствительных путях, который напоминает о брифе, если его нет в `plan.md`, и Stop-хук, который не даёт закончить T2 без ADR. Скилл с описанием «используй перед кодом» на практике не срабатывает, и это измерено.
5. **Рано решил бы, как агент меняет проект Xcode.** Ручная правка `project.pbxproj` — известная ловушка для агентов: конфликты, потерянные файлы, битый проект. Варианты: папки, синхронизируемые Xcode без правки проектного файла, или генерация проекта из описания (XcodeGen, Tuist). Для автономного агента это решение уровня ADR, а в ADR-0001 и в таблице «Отложить» плана его нет. Решать его на шаге скелета, но записать в отложенные сейчас.
6. **Явно задал бы настройки изоляции для каждой цели и пакета.** Подробности в разделе 5.
7. **Первым кодом сделал бы правило дня чтения с тестами.** Это единственный уже утверждённый бизнес-инвариант, и тесты в ADR-0001 расписаны. Система это предусматривает, поправок нет.

### 7.2 Где система даёт обратный эффект

- **Цена.** Обязательный ревьюер на T1 и T2 удваивает цену задач с кодом без измеренной пользы.
- **Ритуал.** Бриф в `plan.md` на каждый T1, включая мелкий баг, и ADR на каждое T2-изменение. Через десяток фич каталог ADR превратится в журнал правок, и найти в нём действующее решение станет труднее.
- **Правило второго круга.** Любая блокирующая находка во втором круге означает «пересмотреть подход» (`reviewer.md:97-99`). Одна мелкая ошибка в исправлении первого круга отправляет автора обратно к брифу. Предсказуемая реакция ревьюера — понижать находки до неблокирующих, чтобы не запускать пересмотр. Оценка, на данных не проверено.
- **Нагрузка на владельца.** Неблокирующие и старые находки идут в `backlog.md` «простым русским» (`CLAUDE.md:50-52`). Бэклог владельца наполнится техническим долгом, который он оценить не может. Пример уже есть: `backlog.md:23-27`.
- **Правила без проверки.** «Ask questions as plain chat text», «one question per message», «at most two rounds», «never start a fresh review to reset rounds», «T2 needs ADR» — модель выполнит их, только если вспомнит. По замеру S3 правило T2 она не выполнила.

### 7.3 Что убрать

- Правило `Bash(git push * HEAD)` и, после серверной защиты, весь список запретов push или его часть.
- Обязательность ревьюера на T1 до пилота на Mac.
- Проход безопасности на любое касание «данных пользователя»: в Slumpy это почти любая фича. Оставить для данных, уходящих с устройства, Keychain, разрешений, ATS и Privacy Manifest.
- Фразу «Read the project context you need: CLAUDE.md» у ревьюера: CLAUDE.md он получает сам.

### 7.4 Чего не хватает

- Серверной защиты `main` и ветки по умолчанию `dev` на GitHub.
- Хуков, которые работают уже сейчас: запрет push в `main` любой формой, напоминание о брифе, проверка ADR при T2.
- У ревьюера — инструмента для чтения документации.
- Решения о том, как агент меняет проект Xcode, в списке отложенных.
- Многотурового продуктового случая и более трудных инженерных случаев в замере.
- Записи в `baseline.md` о том, что правила, добавленные после замера, не измерялись.
