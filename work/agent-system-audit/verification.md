## 0. Главное

Система построена грамотно по замыслу: короткий постоянный контекст, права решений, один ревьюер со строгими критериями находки, решения и ловушки на диске, замеры с сырыми данными. Документация Claude Code использована верно: поля скиллов и агента, загрузка правила по путям и синтаксис разрешений соответствуют текущим страницам. Сырые данные замеров честно сохранены, и все итоговые суммы из них воспроизводятся.

Проблемы сосредоточены в трёх местах: выводы замеров местами сильнее данных; процесс тяжелее, чем нужно, и при этом главные его шаги держатся на дисциплине модели; защита от действий, которые решает владелец, слабее, чем записано. Ложных технических фактов о платформе не найдено; два места неполны (раздел 5).

**Серьёзные находки, по убыванию серьёзности:**

| № | Находка | Серьёзность | Раздел |
|---|---|---|---|
| 1 | Рост цены от ревьюера занижен. В `baseline.md` +61% для ловушек и +140% для проектирования. На одинаковых случаях: +112% и +120%, по отдельным случаям с ревьюером от +58% до +289%. По правилу принятия из плана обязательный ревьюер должен стать кандидатом на снятие обязательности, а в отчёте он помечен как «не проверен» | Высокая | 6.2 |
| 2 | Прирост в продуктовых вопросах частично создан самим замером. Замер однотуровый, а скилл задаёт вопросы по одному. Все 6 ответов «после» содержат ровно один вопрос, поэтому критерии «не больше пяти» и «рекомендация у каждого» проверены на одном вопросе. По главной двусмысленности новая система хуже голой модели: 4 из 6 против 6 из 6. «Дешевле на 35%» относится только к первому вопросу; цена всего процесса спецификации не измерялась | Высокая для выводов | 6.2 |
| 3 | Уровень T2 назначается по области изменения. Почти каждая фича Slumpy трогает хранимые данные и данные пользователя, поэтому почти всё становится T2: бриф с двумя альтернативами, ADR, ревью решения, ревью кода, проход безопасности. Добавление необязательного поля в модель требует ADR и от трёх до шести запусков ревьюера: решение, код в два круга, проход безопасности, перепроверка. | 4 | Главные механизмы держатся на прозе. Бриф не загружается на просьбы о коде, а порядок T2 модель не выполняет, даже когда сама называет T2. Оценка «машинный слой ждёт Mac» верна для сборки, тестов и линтера, но неверна для хуков: по документации хуки работают и в облачных сессиях | Средняя | 3, 8 |
| 5 | Запрет push в `main` обходится четырьмя проверенными формами команды, включая `git push -f`, не касается инструментов GitHub MCP (слияние PR, запись файлов) и при этом запрещает законный `git push -u origin HEAD`. Защиты `main` на GitHub нет. В Project Knowledge записан ложный факт «ветка GitHub по умолчанию — `main`»: по API это `dev` | Средняя: `main` пока не используется для выпуска и ошибочный push можно откатить, но это единственная граница для действия, которое решает владелец | 4 |

## 3. Соответствие документации Claude Code

Источники: `skills.md`, `sub-agents.md`, `memory.md`, `permissions.md`, `hooks.md`, `plugin-evals.md`, `code-review-local.md` с `code.claude.com/docs/en/`, скачаны 27.10.2026. Локальная версия Claude Code 2.1.311.

| Что проверял | Вердикт | Доказательство |
|---|---|---|
| Поля frontmatter скиллов (`name`, `description`) | Верно | Оба поля есть в справочнике frontmatter. Лимит на описание вместе с `when_to_use` — 1 536 символов. Самое длинное описание, у `engineering-design`, около 560 символов |

| Последствие `tools: Read, Grep, Glob, Bash` у ревьюера | **Проблема, средняя** | По документации явный список ограничивает агента этими инструментами: «Inherits every tool available to subagents if omitted». Ревьюер может обойтись только `curl` через Bash, о чём нигде не сказано |
| Получает ли ревьюер CLAUDE.md | Да | «Other built-in and custom subagents load both» (CLAUDE.md и git status). **Вывод.** Правило ловит самую частую форму и мешает одной законной. Форма `git push -f` после перебазирования ветки, отслеживающей `main`, для агента естественна, и она проходит. Кроме того, правила касаются только Bash. Инструменты GitHub MCP в облачных сессиях (`push_files`, `create_or_update_file` с веткой `main`, `merge_pull_request`) ими не покрываются. Это вывод по синтаксису правил; вызовом я не проверял, потому что это запись в настоящий репозиторий.

**Ветка по умолчанию и защита `main`.** Проверено через GitHub API: ветка по умолчанию `dev`, у `main` и `dev` защиты нет (`protected: false`). В `patterns.md:21-22` записано «its default branch is `main`», в разделе 4 плана — «у удалённого репозитория HEAD указывает на `main`». Это устаревший факт (предположение: владелец уже сменил ветку по умолчанию). Он же опровергает мою первоначальную гипотезу о том, что новая облачная сессия откроет `main` со старой системой. Ошибку в гипотезе нашёл субагент проверки согласованности, я перепроверил через API. Остаточный риск низкий: в `main` по-прежнему лежит старая система (коммит a45c5b4, CLAUDE.md под Expo), и сессия, которую явно открыли на `main`, получит её.

**Минимальное исправление.** Включить на GitHub правило защиты `main`: запрет прямого push и force-push, слияние только через PR. Это внешнее действие, оно за владельцем, около 10 минут. Правило срабатывает при любой форме git-команды и при записи в `main` через GitHub MCP. Слияние PR оно не остановит: агент действует от имени владельца. Поэтому в `settings.json` дополнительно запретить целиком инструмент `mcp__github__merge_pull_request` (запрет инструмента по имени надёжен, в отличие от запрета по тексту команды) и `Bash(gh pr merge *)` для Mac. Убрать правило `Bash(git push * HEAD)`. Исправить факт в `patterns.md:21-22` и формулировку «остальное закроет хук на Mac» в `patterns.md:24-25`.

### 6.4 Честность в целом

Оценка: данные честные, оговорки в основном честные, итоговые формулировки в двух местах сильнее данных: «большой прирост» по продуктовым вопросам и цена ревьюера. Ни одна цифра не выдумана; ошибки методические. Правило принятия как текст хорошее, но к самому дорогому механизму применено мягко.

### 7.1 Что сильный senior iOS-инженер сделал бы иначе

Оценки, не проверенные замером.

1. **Защиту `main` поставил бы на сервере.** Правило на GitHub останавливает прямой push и force-push в любой форме, командой или инструментом. Слияние PR закрыл бы запретом конкретного инструмента. Список запретов по тексту команды он считал бы удобством для агента: документация Claude Code прямо пишет, что такие правила не граница безопасности.
2. **Уровень риска привязал бы к принимаемому решению.** Новое хранилище, новая сущность с нестандартной миграцией, новое расширение, новый entitlement, новая зависимость — T2 с ADR. Необязательное поле с лёгкой миграцией и тестом на старых данных — T1. ADR пишется только тогда, когда принимается новое решение.
3. **Ревью назначал бы по сигналу риска.** Свежий ревьюер — на T2 и на изменения общего состояния и многопоточности. На остальное — компилятор, тесты, перечитывание собственного диффа. Это соответствует и правилу принятия из плана.
4. **Ставил бы напоминание в момент действия.** Хук перед правкой `.swift`-файла в чувствительных путях, который напоминает о брифе, если его нет в `plan.md`, и Stop-хук, который не даёт закончить T2 без ADR. Скилл с описанием «используй перед кодом» на практике не срабатывает, и это измерено.
5. **Рано решил бы, как агент меняет проект Xcode.** Ручная правка `project.pbxproj` — известная ловушка для агентов: конфликты, потерянные файлы, битый проект. Варианты: папки, синхронизируемые Xcode без правки проектного файла, или генерация проекта из описания (XcodeGen, Tuist). Для автономного агента это решение уровня ADR, а в ADR-0001 и в таблице «Отложить» плана его нет. Решать его на шаге скелета, но записать в отложенные сейчас.
6. **Явно задал бы настройки изоляции для каждой цели и пакета.** Подробности в разделе 5.
7. **Первым кодом сделал бы правило дня чтения с тестами.** Это единственный уже утверждённый бизнес-инвариант, и тесты в ADR-0001 расписаны. Система это предусматривает, поправок нет.

### 7.2 Где система даёт обратный эффект

- **Цена.** Обязательный ревьюер на T1 и T2 удваивает цену задач с кодом без измеренной пользы.
- **Ритуал.** Бриф в `plan.md` на каждый T1, включая мелкий баг, и ADR на каждое T2-изменение. Через десяток фич каталог ADR превратится в журнал правок, и найти в нём действующее решение станет труднее.
- **Правило второго круга.** Любая блокирующая находка во втором круге означает «пересмотреть подход» (`reviewer.md:97-99`). Одна мелкая ошибка в исправлении первого круга отправляет автора обратно к брифу. Предсказуемая реакция ревьюера — понижать находки до неблокирующих, чтобы не запускать пересмотр. Оценка, на данных не проверено.
- **Нагрузка на владельца.** Неблокирующие и старые находки идут в `backlog.md` «простым русским» (`CLAUDE.md:50-52`). Бэклог владельца наполнится техническим долгом, который он оценить не может. Пример уже есть: `backlog.md:23-27`.
- **Правила без проверки.** «Ask questions as plain chat text», «one question per message», «at most two rounds», «never start a fresh review to reset rounds», «T2 needs ADR» — модель выполнит их, только если вспомнит. По замеру S3 правило T2 она не выполнила.

### 7.3 Что убрать

- Правило `Bash(git push * HEAD)` и, после серверной защиты, весь список запретов push или его часть.
- Обязательность ревьюера на T1 до пилота на Mac.
- Проход безопасности на любое касание «данных пользователя»: в Slumpy это почти любая фича. Оставить для данных, уходящих с устройства, Keychain, разрешений, ATS и Privacy Manifest.
- Фразу «Read the project context you need: CLAUDE.md» у ревьюера: CLAUDE.md он получает сам.

### 7.4 Чего не хватает

- Серверной защиты `main` на GitHub.
- Хуков, которые работают уже сейчас: запрет push в `main` любой формой, напоминание о брифе, проверка ADR при T2.
- У ревьюера — инструмента для чтения документации.
- Решения о том, как агент меняет проект Xcode, в списке отложенных.
- Многотурового продуктового случая и более трудных инженерных случаев в замере.
- Записи в `baseline.md` о том, что правила, добавленные после замера, не измерялись.

## 10. Что не проверено

- **Поведение системы на настоящих задачах.** Платные прогоны не запускались по условию задачи. Всё о работе ревьюера и брифа — по сохранённым ответам замера и по чтению инструкций.
- **Многотуровый продуктовый диалог.** Соблюдает ли агент лимит в пять вопросов на всём диалоге, неизвестно ни мне, ни замеру.
- **Обход запрета через GitHub MCP.** Вывод сделан по синтаксису правил. Вызовом не проверял: это запись в настоящий репозиторий.
- **Работа хуков на Mac и совместимость песочницы с Xcode.** Нужен Mac.
- **Путь агента в замерах.** Трассы удалены, остались итоговые ответы и вердикты.
- **Глобальная конфигурация владельца на будущем Mac** (`~/.claude`). По плану глобальный фреймворк туда не ставится; если поставить, его скиллы с другими именами продолжат срабатывать, а одноимённые перекроют проектные.
