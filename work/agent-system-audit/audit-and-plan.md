## 1. Цель, рамки и принципы

**Главная цель.** Улучшить агентскую систему Claude Code так, чтобы она максимально компенсировала слабости ИИ по сравнению с сильным senior- или staff-инженером iOS. При этом сохранить скорость и разумную стоимость. Почти весь цикл разработки и сопровождения Slumpy будет выполнять Claude Code.

**Роль владельца.** Владелец не программист и код не читает. Он принимает продуктовые и бизнес-решения: UX, брендинг, позиционирование, смысл фич. Техническая ответственность максимально передаётся агентской системе. Владелец не должен становиться техническим руководителем.

**Восемь приоритетов владельца:**

1. Качество рассуждений и выбора архитектуры до написания кода.
2. Простые решения без избыточных абстракций.
3. Системное мышление и оценка последствий изменений.
4. Актуальные платформенные знания и их применение.
5. Независимая критическая проверка собственных решений.
6. Накопление инженерных знаний и защита от повторных ошибок.
7. Максимальная автономность без превращения владельца в техлида.
8. Измеримое повышение качества без чрезмерных расходов токенов и времени.

**Принципы из исходного задания.** Все они действуют.

- **Порядок механизмов.** Что можно проверить машиной, проверяется машиной. Порядок предпочтения: структура проекта и компилятор, затем детерминированные проверки, затем независимое ревью свежим агентом, затем знания по требованию и только потом постоянные инструкции.
- **Минимум постоянного контекста.** Правило, без которого агент не ошибётся, удаляется.
- **Суждение и механизм.** Суждение там, где оно работает. Механизм там, где нужна гарантия. Запрет без механизма контроля в постоянный контекст не добавляется.
- **Глубина по необратимости.** Глубина анализа пропорциональна необратимости решения.
- **Решения вне головы агента.** ADR, соглашения проекта, база ловушек. Устаревшие записи чистятся.
- **Эталон.** Эталон важнее описаний: первый вертикальный срез делается тщательно и служит образцом.
- **Принципы как компромиссы.** Дублирование дешевле неверной абстракции. Абстракция вводится при втором-третьем реальном повторе. Новый слой появляется, только когда у него есть причина.
- **Доказательство.** «Готово» без вывода проверок ничего не значит.
- **Ревью сходится.** Повторная находка исправляется у источника. Число раундов ограничено. Повторная проверка смотрит только новый дифф.
- **Энтропия.** Дрейф, мёртвый код и устаревшие документы убираются постоянно.
- **Гейты защищены.** Отключение правила или ослабление теста требует обоснования и видно на ревью.
- **Субагент только ради изоляции.** Поводы: свежий взгляд, параллельность, измеримое раздувание контекста, конфликт инструкций. Роль сама по себе поводом не является.
- **Цена механизма.** Для каждого механизма понятны: класс ошибок, частота, стоимость и что сломается без него.

**Важная оговорка.** Больше агентов, скиллов и проверок не означает выше качество. Каждый механизм может дать обратный эффект: рост сложности, ритуальные действия, потерю контекста, ухудшение самостоятельности. Поэтому механизм остаётся, только если выигрывает на замере.

**Рабочие допущения.** Продолжаем с ними, пока владелец не скажет иное.

- **Стек:** SwiftUI, минимальная версия iOS 18, выделенный Mac. Обоснование в разделе 11.
- **Расположение системы:** агентская система Slumpy целиком живёт в репозитории. На выделенном Mac глобальный фреймворк для работы над Slumpy не ставится, причина в разделе 8.1.
- **Codex:** файлы не трогаем.
- **Роли:** владелец принимает только продуктовые решения.
- **Язык:** пока только русский.
- **Бюджет:** план Claude уровня Max. Одна сессия агента в каждый момент времени. Ревьюер на каждое нетривиальное изменение. Dynamic workflows по умолчанию не используем.

## 4. Как устроена текущая система

**Проектный слой: файлы репозитория.**

- **`CLAUDE.md`, 2,3 КБ.** Карта проекта, правила языка и поведения, рамки задачи, безопасность. Разделы Language, Behavior, Task Scope и Security повторяют `CLAUDE.md` фреймворка, который по README фреймворка переносится в глобальный `~/.claude/CLAUDE.md`. Сам глобальный файл владельца в аудите не читался.
- **Скилл `project-knowledge`.** Роутер `SKILL.md` на 2,9 КБ и пять справочников на 21,7 КБ: `project`, `architecture`, `patterns`, `deployment`, `ux-guidelines`. Наполнен из черновика `mvp.md`. Описывает React Native, Expo, разработку на Windows и запрет полагаться на Mac.
- **`.claude/settings.json`.** Содержит только `{"agents": {"enabled": true}}`. Такого ключа в справочнике настроек Claude Code нет.
- **`.mcp.json` и `.mcp.bot.json`.** Подключают context7.
- **`.githooks/pre-commit` и `pre-push`.** Вызывают `$HOME/.claude/scripts/sync-to-codex.sh` для синхронизации с Codex. `core.hooksPath` в репозитории не задан, поэтому хуки не активны.
- **`AGENTS.md` и `.codex/skills/`.** Сгенерированное зеркало для Codex.
- **Прочее.** `backlog.md`, `mvp.md`, `work/completed/`.
- **Ветки.** На удалённом репозитории есть `main` и `dev`. По `CLAUDE.md` ветка по умолчанию `dev`, у удалённого репозитория HEAD указывает на `main`.

**Глобальный слой.** Фреймворк molyanov-ai-dev, прочитан по публичному репозиторию, коммит ca44595 от 21.10.2026. По README ставится в `~/.claude`, в облачные сессии не попадает. Локальная копия владельца может отличаться от публичной. Поправка от 27.10.2026: в ветке `dev` фреймворк был скопирован в проект и в облачные сессии попадал, раздел 3.

- **15 агентов:**
  - исследование и спецификация: `code-researcher`, `interview-completeness-checker`, `skeptic`, `userspec-quality-validator`, `userspec-adequacy-validator`;
  - ревью реализации: `code-reviewer`, `test-reviewer`, `security-auditor`, `layout-reviewer`, `documentation-reviewer`, `infrastructure-reviewer`, `prompt-reviewer`;
  - ревью скиллов: `skill-checker`, `skill-logic-reviewer`, `skill-simplicity-reviewer`.
- **13 скиллов:** `methodology`, `project-initialization`, `documentation-writing`, `user-spec-planning`, `code-writing`, `layout-writing`, `infrastructure-setup`, `prompt-master`, `skill-master`, `test-master`, `code-reviewing`, `layout-reviewing`, `security-auditor`. Шаблон `project-knowledge` лежит внутри `project-initialization`.
- **Объём.** Файлы `SKILL.md` и описания агентов занимают около 152 КБ, вместе со справочниками скиллов около 240 КБ. Прописных MUST две штуки, NEVER три, ALWAYS две: система написана под современные модели и не перегружена запретами.

**Методология.**

- **Планирование фичи.** Интервью идёт пачками по 3–4 вопроса, пока каждая тема не заполнена на 85%. Затем `code-researcher`, проверка полноты интервью и `user-spec.md`. После этого три валидатора в параллель, до трёх раундов, и одобрение владельца.
- **Реализация.** Нужные скиллы исполнения, затем параллельные ревьюеры. Находки показываются владельцу, исправления только после его одобрения.
- **Финализация.** Обновление Project Knowledge и перенос фичи в `work/completed`.

## 5. Оценка: насколько текущая система компенсирует слабости ИИ

### 5.1 По восьми приоритетам владельца

| Направление | Что есть сейчас | Вердикт | Главный пробел |
|---|---|---|---|
| 1. Рассуждение до кода | Интервью, исследователь кода, три валидатора спецификации. В `code-writing` есть шаг «объясни подход и жди одобрения», но только для незапланированной работы | Частично | Спецификация описывает поведение. Технические решения по одобренной спецификации принимаются прямо в коде без альтернатив и без проверки. Темы `technical_decisions` и `data_requirements` в интервью необязательны |
| 2. Простота | Сильные формулировки в `code-writing` и `code-reviewing`. У валидатора есть пункт про оверинжиниринг | Частично, только проза | Нет эталона и машинных сигналов. Пункт про недоинжиниринг требует разобрать пустые данные, таймауты, дубли и прерывания для каждого сценария. Правило «не скрывай находку из-за редкости» давит в сторону усложнения |
| 3. Системное мышление | Ревью читает вызывающий код и контракты, исследователь ищет точки интеграции | Частично | Нет карты реальной архитектуры, журнала решений и оценки последствий. Валидатор отбрасывает «гипотетическую будущую нагрузку» целиком |
| 4. Платформенные знания | Правило «всегда используй context7» | Не покрыто | Ничего про Swift и iOS. Модели знают мир примерно до июня 2026, а iOS 27 и Xcode 27 вышли в сентябре 2026 |
| 5. Независимая критика | Свежий контекст. Объяснение исполнителя проверяется как утверждение. Формат находки с местом, доказательством и последствием | Частично, основа хорошая | Нет машинного слоя до ревью, проверки находок, схождения и уровней риска. Находки уходят владельцу |
| 6. Накопление знаний | Project Knowledge с одним владельцем факта, финализация, `decisions.md` у каждой фичи | Частично | Нет сводного журнала решений и файла ловушек. Повторные находки не превращаются в правила |
| 7. Автономность | Владелец одобряет технические находки и точный дифф документации, отвечает на технические вопросы интервью | Работает против цели | Тема интервью `integration_points` обязательна. Владелец становится техлидом |
| 8. Измеримость и цена | Нет | Не покрыто | На одну фичу от 7 до 16 и больше запусков субагентов плюс циклы одобрения владельцем |

**Как посчитаны запуски.**

- Исследователь кода: один запуск.
- Проверка полноты интервью: минимум один.
- Три валидатора спецификации: до трёх раундов, до девяти запусков.
- Ревьюеры реализации: от одного до четырёх.
- Ревьюер документации при финализации: один.

Минимум 7 запусков при одном раунде валидации и одном ревьюере. До 16 и больше при трёх раундах, повторных проверках полноты и четырёх ревьюерах.

**Что работает и остаётся:**

- **Дисциплина объёма.** Находка не расширяет полномочия. Выбирается минимально достаточное решение.
- **Позиция ревьюера.** Свежий контекст. Объяснение исполнителя проверяется как утверждение. У находки есть место, доказательство и последствие. Чистый результат допустим.
- **Устройство Project Knowledge.** Роутер, правило одного владельца факта, загрузка по требованию.
- **Философия тестов из `test-master`.** Защищать поведение на самой маленькой надёжной границе. Лакмус: если удалить строку логики, тест должен упасть.
- **Финализация фичи.** Обновление долговременной документации.

### 5.2 Подтверждённые проблемы

1. **Ложная техническая основа.** Project Knowledge и README описывают React Native, Expo и разработку на Windows без Mac (`architecture.md`, `patterns.md`, `deployment.md`). Агент будет следовать этому.
2. **Нет iOS-содержимого.** `layout-writing` работает по ширинам 360, 430, 768 и 1440 и скриптам Playwright. `security-auditor` проверяет XSS, CSRF и SSRF. `infrastructure-setup` описывает Docker и gitleaks. Для iOS это источник ложных правил.
3. **Нет машинных гейтов.** Нет линтера, CI и хуков Claude Code. В `settings.json` единственный ключ не документирован.
4. **Хуки зависят от машины.** Git-хуки вызывают скрипты из `$HOME/.claude/scripts`. В облаке они не активны. Если на новом Mac включить хуки без этих скриптов, каждый push будет падать.
5. **Дубли постоянного контекста.** Разделы проектного `CLAUDE.md` повторяют глобальный. При расхождениях инструкции конфликтуют: «EAS secrets» против «.env, config files».
6. **Устаревшие и лишние инструкции.** «Use TodoWrite for multi-step tasks (>1 step)» в CLAUDE.md фреймворка повторяет то, что модель делает сама. «EAS secrets» привязаны к Expo.
7. **Неверные точки остановки.** `code-writing`, `skill-master/references/agents.md` и `documentation-writing` требуют, чтобы владелец одобрял технические находки и дифф документации.
8. **Ревью не сходится.** Нет повторного прохода только по новому диффу. Лимит раундов есть только у спецификации. Механизма «повторная находка становится правилом» нет.
9. **Нет памяти решений.** `decisions.md` уезжает в `work/completed`. Сводного журнала решений и базы ловушек нет.
10. **Нет инженерной глубины.** Нет вопросов опытного инженера перед новым модулем, моделью данных или интеграцией. Нет Swift-рубрики у ревьюера.
11. **Дорогое планирование.** От 5 до 11 и больше запусков агентов на одну спецификацию.
12. **Дублирование встроенного.** `code-reviewer` повторяет встроенный `/code-review`, `skill-master` повторяет `skill-creator`, интервью и план частично повторяют режим планирования.
13. **Интервью как конечный автомат.** Пороги 85%, шкалы оценок, сохранение после каждого ответа. Собственный `skill-simplicity-reviewer` фреймворка перечисляет такие вещи как признаки переусложнения.
14. **context7 для Apple не проверен.** Официальную документацию Apple можно получать напрямую в markdown.
15. **Порча инструкций при конвертации.** В `AGENTS.md` появилась бессмысленная фраза «NEVER use plain chat question tool».
16. **Конфликт приоритетов скиллов.** Глобальные скиллы имеют приоритет над проектными с тем же именем. Глобальный фреймворк на Mac продолжит навязывать свои правила, например «жди одобрения находок».

### 5.3 Риски

1. **Сроки Apple.** Сроки одобрения distribution entitlement для Family Controls непредсказуемы, а без платного аккаунта блокировку не проверить даже на своём телефоне.
2. **Устаревшие знания модели.** Модели знают мир примерно до июня 2026. iOS 27, Xcode 27 и Swift 6.4 вышли позже.
3. **Общие слепые пятна.** Ревьюер работает на той же модели, что и исполнитель.
4. **Разное поведение в облаке и на Mac.** Облачные сессии не видят глобальных скиллов и auto memory.
5. **Дрейф Codex.** Файлы Codex расходятся с источниками без работающих хуков.
6. **Оплата вне App Store.** При наличии iOS-приложения есть риск по правилу 3.1.1.
7. **Цена замеров.** Замеры сами по себе стоят токенов и времени.

## 8. Целевая система

### 8.1 Принцип и состав

**Принцип.** Модель знает принципы проектирования, механику языка и стандарты. Слабость в том, что в момент решения она их не применяет. Пересказ учебника в постоянных инструкциях дорог и плохо помогает. Поэтому система работает по четырём направлениям:

- заставляет применить знание в точке решения;
- проверяет применение свежим взглядом там, где ошибка дорогая;
- переносит гарантии в компилятор и скрипты;
- хранит решения и ловушки на диске.

**Состав.** Предложение, ещё не внедрено.

- **`CLAUDE.md`, около 60 строк.** Карта продукта, права решений, уровни риска, определение готовности, ссылки, строка о том, что сохранять при сжатии контекста: изменённые файлы, шаг плана, команды проверки. При варианте B для Codex общие инструкции живут в `AGENTS.md`, а `CLAUDE.md` подключает его через `@AGENTS.md`.
- **`.claude/rules/swift.md`.** Подгружается только при работе со `.swift`, около 20 строк фактов, которые модель сама не выведет: минимальная версия и политика доступности API, Swift 6 strict, default MainActor isolation, обязательный Liquid Glass при сборке в Xcode 27, ограничения памяти расширений, рецепт поиска документации Apple.
- **Скилл `project-knowledge`.** Существующий, с исправленными фактами. Добавляются карта реальной архитектуры, индекс решений, ссылка на файл ловушек, бизнес-инварианты вроде правил «сегодня».
- **Скилл `engineering-design`.** Проектный бриф, меню вопросов по типу решения, разведка области.
- **Скилл `product-spec`.** Упрощённая спецификация: до 5 продуктовых вопросов, шаблон, проверка глазами исполнителя.
- **Скилл запуска и проверки.** Генерируется на Mac через `/run-skill-generator`.
- **Агент `reviewer`.** Единственный кастомный агент. Режимы: спецификация, решение, код, перепроверка находок. Рубрика лежит в описании агента, раздел 8.4. Меню вопросов агент получает, предзагружая скилл `engineering-design` через поле `skills`.
- **Два хука в `.claude/settings.json`.**
  - После правки `.swift`: форматтер и линтер только по этому файлу.
  - При старте сессии: ветка, свободное место на диске, текущий `plan.md`.
- **Правило разрешений** в том же файле запрещает push в `main`.
- **Скрипт `scripts/check`.** Сборка, тесты пакета и приложения, линтер, формат, сканер обхода гейтов, расчёт минимального уровня риска по изменённым путям. Пишет запись о прогоне с коммитом и временем.
- **Документы.** `docs/decisions/NNNN-*.md` для ADR, `docs/lessons.md` для ловушек, `work/{feature}/spec.md` и `work/{feature}/plan.md`.
- **Замеры.** `evals/` для компонентных случаев, `scripts/eval/` для сквозного стенда.

**Глобальный фреймворк на Mac.** Глобальные скиллы имеют приоритет над проектными с тем же именем. Кроме того, глобальные скиллы с другими именами продолжат срабатывать и навязывать правила вроде «жди одобрения находок». Поэтому на выделенном Mac для Slumpy глобальный фреймворк не ставится. Для замера варианта V0 он ставится в отдельную папку конфигурации.

### 8.2 Уровни риска

> **Пересмотрено 27.10.2026 после независимой проверки** (`verification.md`). Действующие уровни и правила ревьюера — в CLAUDE.md, отступления от этого раздела — в `deviations.md`, строки 2, 12, 14, 15 и 19. Таблица ниже — исходный план.

| Уровень | Примеры | Что обязательно | Доп. запусков модели |
|---|---|---|---|
| T0 Мелочь | Текст, цвет, правка в одном месте без новых типов | `check` | 0 |
| T1 Обычная задача | Фича или баг в существующих границах | Короткий бриф в `plan.md`, `check`, один ревьюер, не больше двух раундов | 1–2 |
| T2 Необратимое | Хранимая модель и миграции. Границы модулей и общий пакет. Многопоточная архитектура. Системные сервисы и расширения. Сеть, бэкенд, вход, приватность, деньги. Новая сторонняя зависимость | Бриф с двумя альтернативами и ценой замены через год. ADR. Ревью решения до кода. Ревью кода. Перепроверка спорных находок. Продуктовые последствия идут владельцу | 3–5 |

Уровень предлагает агент. `check` по изменённым путям считает минимально допустимый уровень и падает, если заявлен более низкий. Примеры путей: слой хранения, миграции, `Package.swift`, entitlements, `Info.plist`, цели расширений. Это аналог классификатора риска команды Claude Code, описанного во вторичных источниках.

Для сравнения: сейчас на фичу уходит от 7 до 16 и больше запусков субагентов. В целевой системе T1 стоит 2–3 запуска вместе с проверкой спецификации, T2 стоит 4–6.

### 8.3 Обязательные механизмы

**1. Короткий и правильный постоянный контекст.**

- **Слабость:** агент следует ложным и устаревшим инструкциям, переограничение.
- **Тип и почему:** постоянный контекст, потому что права решений и карта нужны в каждой сессии. Всё остальное грузится по требованию.
- **Как работает:** исправить факты, убрать дубли с глобальным CLAUDE.md, вынести Swift-факты в правило по путям.
- **Цена:** почти нулевая.
- **Обратный эффект и защита:** со временем контекст разрастается. Каждую строку проверяем вопросом «без неё агент ошибётся?». Раз в месяц запускаем `/doctor prompt-audit`.

**2. Машинный слой до любого ревью.**

- **Слабость:** ложное «готово», ошибки потоков, устаревшие API, обход проверок.
- **Тип и почему:** компилятор и детерминированные проверки. Они дают гарантию дешевле любого агента.
- **Как работает:**
  - Swift 6 language mode со строгой проверкой многопоточности.
  - Минимальная iOS 18: компилятор сам требует проверку доступности для новых API.
  - Предупреждения считаются ошибками в CI.
  - `check` как единая точка входа. Сканер обхода ищет новые отключения правил линтера, конструкции из списка в `.claude/rules/swift.md`, удалённые или ослабленные проверки в тестах.
  - Хук после правки `.swift`.
- **Определение готовности:** в отчёте вывод `check` на текущем коммите.
- **Цена:** 1–2 дня настройки, минуты на задачу.
- **Обратный эффект и защита:** агент режет файлы ради лимитов или спорит с линтером. Правил мало, и они про структуру. Лимиты размера работают как предупреждения. Любое отключение требует комментария с причиной и видно ревьюеру.

**3. Проектный бриф перед кодом.**

- **Слабость:** молчаливые допущения, первая попавшаяся архитектура, популярное решение вместо подходящего, знание без применения.
- **Тип и почему:** скилл, подгружается на T1 и T2, потому что вопросы нужны только при решениях.
- **Как работает:** бриф лежит в `plan.md` и начинается с того, что дороже всего менять:
  - модель данных;
  - границы и контракты;
  - пользовательские сценарии.

  Дальше:
  - допущения;
  - что ещё затронуто: кто ещё читает и пишет это состояние, что меняется для расширений, какая нужна миграция;
  - на T2 две альтернативы с обратимостью;
  - по строке на каждый новый тип, протокол, слой, зависимость или настройку: зачем сейчас и почему проще нельзя;
  - ответы только на вопросы меню, относящиеся к изменению, раздел 8.4.

  Внизу плана журнал хода работы и отклонений.
- **Цена:** минуты.
- **Обратный эффект и защита:** ритуальное заполнение и план длиннее кода. Лимит объёма. Пустые разделы удаляются. Ревьюер сверяет ответы с кодом.

**4. Один ревьюер в свежем контексте с правилами схождения.**

- **Слабость:** самопроверка предпочитает свои решения. Ревью может само порождать усложнение.
- **Тип и почему:** субагент, потому что изоляция контекста здесь и есть смысл.
- **Как работает:**
  - Режимы: спецификация, решение, код, перепроверка.
  - Находка считается, только если это:
    - баг с реалистичным путём к сбою;
    - нарушение спецификации или инвариантов проекта;
    - сложность с названной ценой.
  - Не больше двух раундов, второй смотрит только новый дифф и открытые находки.
  - Повторяющийся класс находок исправляется у источника в той же задаче.
  - На T2 спорные находки перепроверяет второй запуск.
  - Агент исправляет сам. Владельцу уходит только то, что меняет продукт.
- **Цена:** 1–2 запуска на T1.
- **Обратный эффект и защита:** ревьюер, которому велено искать, всегда что-то найдёт. Помогают критерии находки и лимит раундов.

**5. Решения и ловушки на диске.**

- **Слабость:** нет памяти между сессиями, решения расходятся, ошибки повторяются.
- **Тип и почему:** документы по ссылке.
- **Как работает:**
  - ADR для T2: контекст, решение, отвергнутые альтернативы, последствия, обратимость, когда пересмотреть.
  - Файл ловушек: симптом, причина, где теперь защищено, когда устареет. Запись делается, только если без неё будущий исполнитель, читая код, вероятно повторит ошибку.
  - Лестница исправления у источника: компилятор, затем линтер, тест, скилл, ловушка и только потом CLAUDE.md.
  - Финализация фичи обновляет карту архитектуры и индекс решений.
- **Auto memory:** допустима для предпочтений владельца. Она живёт только на одной машине и не видна в облаке, поэтому решения проекта хранятся только в репозитории.
- **Цена:** минуты.
- **Обратный эффект и защита:** записи устаревают. Поле «когда устареет» и периодическая уборка.

**6. Права решений и интерфейс владельца.** Раздел 8.5.

**7. Актуальность платформы.**

- **Слабость:** API и паттерны прошлых лет, незнание того, что вышло после июня 2026.
- **Тип и почему:** компилятор плюс знания по требованию.
- **Как работает:**
  - Короткий справочник проекта.
  - Рецепт: к адресу страницы документации Apple добавляется `.md`, и страница возвращается в markdown. Проверено 26.10.2026.
  - Для API, появившегося после середины 2026 или вызывающего сомнение, агент сверяется с документацией до использования.
  - Найденные платформенные ловушки уходят в файл ловушек.
- **Обратный эффект и защита:** справочник превращается в учебник. В нём остаётся только то, в чём модель доказуемо ошибается.

**8. Замер на одинаковых задачах.** Раздел 9.

**9. Разведка области.**

- **Слабость:** меню вопросов срабатывает, когда агент уже знает, о чём спрашивать. В незнакомой области он может этого не знать.
- **Когда:** перед первым серьёзным решением в новой для проекта области. Примеры: Screen Time, синхронизация, HTTP-кеширование, платежи, вход.
- **Как работает:** короткий разбор слепых зон:
  - что знают опытные специалисты и упускают новички;
  - какие стандарты и протоколы действуют;
  - где обычно всё ломается.

  Каждый пункт сверяется с первоисточниками. Результат сохраняется справочником области на одну страницу. Исследование можно отдать субагенту, чтобы не засорять контекст.
- **Цена:** один раз на область.
- **Основание:** blind spot pass из field guide Anthropic по Fable.

### 8.4 Как система ориентируется в инженерных тонкостях

Конкретные знания у модели есть: протекающие абстракции, SOLID, DRY, KISS, диспетчеризация, протоколы и стандарты. Слабость в применении. Механизм не зависит от стека.

**Меню вопросов по типу решения.** Используется в брифе. Агент отвечает только на относящиеся вопросы, одной-двумя строками.

| Тип решения | Вопросы |
|---|---|
| Новая абстракция, тип, модуль или граница | Что протечёт наружу: ошибки хранилища, асинхронность, потоки, время, сеть? Что будет со второй реализацией? Кто владеет состоянием? Какой контракт: входы, выходы, ошибки, порядок, потокобезопасность? |
| Данные и рост | Что произойдёт при росте в 10 и в 100 раз: память, время запуска, плавность прокрутки, размер базы, время миграции? Как пройдёт миграция? Насколько решение обратимо, сколько будет стоить замена через год? |
| Взаимодействие частей, сервисов, расширений | Какой контракт обмена? Что будет при сбое или задержке другой стороны? Гарантирован ли порядок? Возможны ли дубли? |
| Многопоточный код | Где изоляция, что `Sendable`, кто владеет состоянием? Что с отменой? Что выполняется на главном потоке? |
| Системный сервис или внешний API | Что при отказе в разрешении? Что в разных версиях iOS? Какие фоновые лимиты? Что без сети? Что требуют App Review и правила приватности? |
| Стандарт или протокол | Какой стандарт действует и что он требует? Читаем первоисточник: RFC, ISO 8601, часовые пояса IANA, семантика HTTP, OAuth и Sign in with Apple, APNs, Unicode, WCAG и Apple HIG, App Store Review Guidelines. По памяти не отвечаем |
| Интерфейс | Dynamic Type, VoiceOver, тёмная тема, маленькие экраны, производительность списков |
| Любое | Можно ли проще? |

**Рубрика ревьюера.** Механика языка видна в коде, поэтому проверяется здесь:

- value или reference семантика, и почему;
- статическая или динамическая диспетчеризация и её цена на горячих путях;
- протоколы с associated types, дженерики против `any`;
- ARC, циклы ссылок, захват в замыканиях;
- изоляция акторов и `Sendable`;
- доступность API для iOS 18 и мягкие устаревания, о которых компилятор молчит;
- тесты на правильной границе.

SOLID, DRY и KISS в рубрике описаны как компромиссы:

- дублирование дешевле неверной абстракции;
- абстракция вводится при втором-третьем реальном повторе или при реальной границе, например шов для системного сервиса ради тестов;
- новый слой появляется, только когда у него есть причина.

**Накопление.** Каждая найденная тонкость попадает в файл ловушек или в справочник области.

**Ограничения.**

- Если модель не знает тонкость и не находит её в источниках, система её не создаст.
- Ревьюер на той же модели разделяет часть её слепых пятен.

Поэтому в замер входят задачи-ловушки по каждой категории, раздел 9.

### 8.5 Права решений и интерфейс владельца

**Владелец решает:**

- что пользователь увидит или почувствует;
- объём;
- приватность и данные пользователей;
- деньги;
- внешние действия: push в `main`, App Store Connect, TestFlight, публикации.

**Система решает и записывает:** всё остальное. Необратимые решения уходят в ADR и проходят ревью решения.

**Вопросы владельцу:**

- Задаются на этапе спецификации, до пяти на фичу, по одному.
- Отбираются по влиянию и неопределённости.
- У каждого вопроса: суть, почему важно, варианты, рекомендация, что изменится для читателя.
- Во время реализации вопрос задаётся только при отклонении, заметном пользователю. Иначе агент выбирает консервативный вариант и записывает отклонение в `plan.md`.

**Отчёт о задаче:**

- что изменилось для пользователя;
- снимки экранов: светлая и тёмная тема, крупный шрифт, iOS 18 и актуальная версия;
- что проверено: краткий вывод `check`;
- какие решения приняты, простыми словами;
- отклонения;
- что проверить руками на iPhone, готовым чеклистом, если нужно.

Когда нужен ответ, приходит push-уведомление через Remote Control.

**Обратный эффект и защита:** возможен тихий дрейф продукта. Защищают приёмка по снимкам и отклонения в каждом отчёте.

### 8.6 Архитектура агентов

| Агент сейчас | Изоляция и потери | Решение |
|---|---|---|
| `code-researcher` | Чтение многих файлов вне основного контекста, оправдано | Заменить встроенным Explore с задачей из скилла |
| `code-reviewer` | Свежий взгляд, оправдано | Стать единственным `reviewer` с режимами и Swift-рубрикой |
| `test-reviewer` | Тот же дифф отдельным лейном | В раздел тестов рубрики |
| `security-auditor` | Веб-риски | В условный раздел рубрики: Keychain, ATS, Privacy Manifest, приватность. Отдельный проход только на T2 |
| `userspec-quality-validator`, `userspec-adequacy-validator`, `skeptic`, `interview-completeness-checker` | Четыре чтения одного документа, до трёх раундов | Один режим «спецификация» у `reviewer`: проверка глазами исполнителя, один раунд, второй только по изменениям |
| `documentation-reviewer` | | Убрать. Чеклист в финализации |
| `infrastructure-reviewer`, `layout-reviewer` | Для iOS неприменимо | Убрать из проекта |
| `prompt-reviewer`, три ревьюера скиллов | Промптов в продукте нет | Убрать из проекта. Для скиллов `/doctor prompt-audit` и `/skill-doctor` |

Итог: один кастомный агент с четырьмя режимами и встроенный Explore. Вариант «встроенный `/code-review` вместо своего ревьюера» проверяется гипотезой H2.

### 8.7 Экспериментальные гипотезы

| Гипотеза | Как проверяем |
|---|---|
| H1. Голый Claude Code с тем же `check` не хуже полной системы | Те же задачи без системы. Если разницы нет, механизм лишний |
| H2. Встроенные `/code-review` и `/simplify` работают не хуже своего ревьюера с рубрикой | Заложенные дефекты: доля найденных, ложные находки, цена |
| H3. Ревью решения до кода на T2 окупается | Сценарии проектирования с ним и без. Переделки в сквозных задачах |
| H4. Проверка спецификации свежим агентом снижает вопросы и отклонения во время реализации | Число вопросов и отклонений |
| H5. Отобранные Swift-скиллы повышают платформенную корректность | Задачи с ними и без |
| H6. `/goal` или Stop-хук снижают ложное «готово» сверх правила с выводом `check` | Число ложных «готово» |
| H7. Снимочные тесты экранов окупаются | Пойманные визуальные регрессии против нестабильности |
| H8. Перекрёстная проверка другой моделью снижает самопредпочтение на T2 и в оценке замеров | Расхождения с проверкой той же моделью |
| H9. Periphery находит мёртвый код, который пропускает ревьюер | Число находок сверх ревью |
| H10. Превью и поиск Xcode MCP полезнее markdown-страниц Apple | Качество платформенных решений |

### 8.9 Codex: цена второго рантайма и упрощение

**Цена сейчас:**

- **Устаревшая раскладка.** В репозитории лежат сгенерированные `AGENTS.md` и шесть файлов в `.codex/skills`. Фреймворк с 21.10.2026 генерирует скиллы Codex в `.agents/skills`.
- **Скрипты вне репозитория.** Около 135 КБ Python, от которых зависят оба git-хука. Если включить хуки на Mac без этих скриптов, каждый push будет падать.
- **Лишняя работа.** Каждая правка `.claude` требует синхронизации и проверки сгенерированного. Инструкции об этом сидят в двух глобальных скиллах и занимают контекст.
- **Порча инструкций.** Конвертер уже исказил правило в `AGENTS.md`.
- **Главная цена.** Общий слой тянет систему к наименьшему общему знаменателю. Самые полезные механизмы этого плана есть только в Claude Code: хуки, правила по путям, субагент с предзагруженной рубрикой, `/goal`.

**Польза:** вторая модель для перекрёстной проверки и оценки, гипотеза H8.

**Варианты без удаления:**

- **A. Заморозка.** Синхронизацию не запускать, хуки не включать, сгенерированные файлы пометить как неподдерживаемые.

Скиллы для Codex доступны по симлинку `.agents/skills`. Конвертер не нужен. Claude Code читает `AGENTS.md` напрямую, если нет `CLAUDE.md`, и через импорт в остальных случаях.
- **C. Codex как инструмент.** Скрипт вызывает Codex в неинтерактивном режиме только для перекрёстной проверки и оценки.

**Рекомендация.** Сейчас вариант A. Потом B или C по результату H8. Удаление только с согласия владельца.

### 8.10 Что система закрывает и насколько

| Слабость | Механизм | Насколько |
|---|---|---|
| Ложное «готово», обход проверок | `check`, сканер обхода | Сильно, это машина |
| Многопоточность, доступность API | Компилятор в строгом режиме | Сильно для пойманных классов ошибок |
| Утечки памяти, производительность | Рубрика ревьюера. Instruments позже | Частично |
| Плохая архитектура, молчаливые допущения | Бриф до кода, ревью решения на T2, разведка области | Средне: часть ошибок ловится до кода, но проверяет та же модель |
| Переусложнение | Строка «почему проще нельзя», критерии находок, эталон | Средне, нужен замер |
| Устаревшие знания платформы | Документация Apple, справочник, компилятор | Частично |
| Повторные ошибки, расхождение решений | ADR, файл ловушек, исправление у источника | Хорошо при дисциплине записей |
| Владелец в роли техлида | Права решений, продуктовые вопросы, отчёт со снимками | Хорошо |
| Деградация в длинной сессии | `plan.md` с журналом, одна задача на сессию, инструкция для сжатия | Хорошо |

**Честная граница.** Гарантию дают только машинные проверки. Архитектура и простота остаются суждением модели. Система делает это суждение явным, проверяемым и накапливаемым, но не превращает модель в staff-инженера. Насколько вырастет качество, покажет только замер.

## 9. Как измеряем эффект

**Принципы из набора Anthropic.**

- Одна правка на вариант.
- Модель и уровень усилия закреплены.
- Оцениваем результат, путь к нему не оцениваем.
- Сравниваем перевернувшиеся задачи, а не только средний балл.
- Ошибки в самом eval исправляем до замеров.
- Механизм с нулевой разницей удаляется.

**Компонентные замеры: дешёвые, без сборки, до покупки Mac.**

Инструмент: `claude plugin eval`. Он сам считает разницу с плагином и без него, умеет ставить потолок цены и использовать модель-судью. Документация упоминает ранний доступ.

Ограничения: каждый прогон идёт в пустой рабочей папке, а проектная конфигурация, созданная подготовительным скриптом, не загружается. Поэтому проверяемая система упаковывается как плагин: скиллы и агент. Правила из CLAUDE.md на время замера переносятся в скилл. Если это искажает сравнение или инструмент недоступен, тот же набор прогоняется скриптом через `claude -p` с отдельной папкой конфигурации на каждый вариант.

Случаи:

- **9 диффов с заложенными дефектами для ревьюера:**
  1. протекающая абстракция: ошибки хранилища доходят до View;
  2. гонка через `@unchecked Sendable`;
  3. «сегодня» через `Calendar.current` без явного часового пояса;
  4. цикл ссылок в таймере;
  5. протокол с единственной реализацией и фабрикой;
  6. мёртвый код после изменения;
  7. забытая миграция хранимой модели;
  8. мягко устаревший API;
  9. ослабленный тест.

  Предлагаемая цель: найти не меньше 7 из 9 при не больше чем 2 ложных находках.
- **4 сценария проектирования для брифа:** цели чтения, выбор хранилища, общий код с расширением, обмен с будущим сервером.
- **3 двусмысленных продуктовых запроса:** проверяем, что вопросы продуктовые, их не больше пяти и у каждого есть рекомендация.
- **Ловушки по категориям тонкостей:** протекающая абстракция, немасштабируемое решение, нарушение стандарта, ошибка механики языка, сбой взаимодействия частей.
- **Срабатывание скиллов** на естественных формулировках.

**Сквозные замеры на Mac.**

| Задача | Что проверяет | Скрытая проверка |
|---|---|---|
| 1. Цели чтения: книга к дате, N книг за сезон | Рассуждение до кода, модель данных | Тесты правил, оценка брифа |
| 2. Минуты «сегодня» при сессии через полночь, переходе на летнее время, поездке | Системное мышление, стандарты времени | Тесты с часовыми поясами |
| 3. Сортировка библиотеки | Простота | Размер диффа, новые типы |
| 4. Таймер в фоне и Live Activity | Многопоточность, жизненный цикл | UI-тест, ошибки изоляции |
| 5. Отказ в доступе к камере для фото цитаты | Разрешения, краевые случаи | UI-тест с отозванным разрешением |
| 6. Баг с ложным симптомом | Поиск корневой причины | Тест на корневую причину |
| 7. Новое поле в сохранённой модели при наличии данных | Миграции | Тест на старых данных |
| 8. Задача, где проще всего ослабить тест или отключить правило | Обход гейтов | Сканер обхода |
| 9. Изменение с продуктовым компромиссом | Автономность, вопросы владельцу | Лист ответов, тип вопросов |
| 10. Новый API с запасным вариантом для iOS 18 | Актуальность платформы | Сборка и тесты на двух версиях |

**Порядок прогона.**

1. Все варианты стартуют с одного коммита: скелета после опыта с инструментами.
2. Три варианта:
   - V0: текущая система, в Project Knowledge исправлены только факты;
   - V1: голый Claude Code с минимальным CLAUDE.md и тем же `check`;
   - V2: новая система.

   Каждый вариант работает в своей папке конфигурации через `CLAUDE_CONFIG_DIR`, чтобы глобальные скиллы не смешивались.
3. Каждый прогон идёт в свежей копии репозитория через `claude -p`. Режим `--permission-mode auto` и `--permission-prompts none`, чтобы прогон не ждал ответа на запрос разрешения. Вывод `--output-format json`, стоимость берётся из поля `total_cost_usd`.
4. Если агент заканчивает ход вопросом, скрипт отвечает из листа ответов через `--resume`. На вопрос вне листа отвечает «реши сам и запиши допущение» и засчитывает его.
5. После прогона в копию добавляются скрытые тесты, запускаются `check` и скрипт метрик.
6. В пилоте два повтора на задачу, для решений три.
7. Качество решений оценивает отдельный агент по рубрике, вслепую и попарно, тремя голосами. Перекрёстная оценка другой моделью проверяется как H8.

| Метрика | Как считаем |
|---|---|
| Корректность | Доля пройденных скрытых тестов |
| Ложное «готово» | Агент заявил «готово», а `check` или скрытые тесты красные |
| Простота | Добавленные строки, новые типы и протоколы, предупреждения сложности, мёртвый код |
| Объём | Файлы вне ожидаемой области |
| Обход гейтов | Отключения и ослабления без обоснования |
| Нагрузка на владельца | Число вопросов и доля технических. Цель для технических: ноль |
| Качество решений | Оценка брифа и кода по рубрике |
| Цена | Стоимость, время, число ходов |
| Ревью | Раунды на правку, доля подтверждённых находок, доля находок по коду, который был до правки, число выходов «пересмотреть подход» |

**Правило принятия.** Механизм остаётся, если с ним корректность не хуже и ни одна задача не перевернулась в провал без объяснимой причины. Рост цены при этом не должен превышать порог 25%. Механизм с нулевой разницей удаляется.

**Объём.** Пилот: 6 задач, 2 варианта, 2 повтора, всего 24 прогона, примерно ночь работы Mac. Полный замер, 10 задач на 3 варианта по 3 повтора, всего 90 прогонов, делаем, только если пилот ничего не показал.

**Вертикальный срез как экзамен системы.** Он должен показать, насколько система сама принимает и реализует качественные инженерные решения.

- **Вход:** владелец даёт только продуктовый бриф, без технических подсказок.
- **Что задевает срез:** решения уровня T2:
  - хранимая модель сессии, готовая к новым типам чтения без переделки и без лишнего обобщения;
  - отнесение минут к дню;
  - Live Activity и жизненный цикл приложения;
  - общий код с расширением.
- **Оценка:**
  - те же метрики;
  - глубокий аудит свежим ревьюером по рубрике;
  - отдельный агент пишет состязательные тесты против готового кода;
  - учёт вмешательств владельца и их типа.
- **Варианты:** V2. Если позволит бюджет, параллельно V1 в отдельной копии. Это прямой ответ, лучше ли система голой модели на реальной задаче.
- **Образец:** срез становится образцом для следующих фич только после аудита.

## 11. Условия для системы: стек, проверка, среда, дизайн

### 11.1 SwiftUI или Expo

**Рекомендация: SwiftUI.**

- Блокировка, экран блокировки, монитор активности и интерфейс Live Activity в Expo всё равно пишутся на Swift в отдельных расширениях.
- `react-native-device-activity` требует собственной сборки клиента. `expo-widgets` находится в стадии alpha с 04.03.2026.
- Самая рискованная часть нативна в обоих вариантах. Expo добавляет второй язык и вторую систему сборки, а это лишние места поломки для автономного агента.

**Что теряем:**

- общий код с Android;
- обновления без ревью App Store;
- сборку и тесты в облачных сессиях Claude. Со SwiftUI всё выполняется только на Mac.

**Когда пересмотреть.** Если Android понадобится в пределах примерно полугода после iOS или монетизация будет держаться на Google Play и RuStore. Доля Android в мобильном трафике России в июне 2026 составила около 66% по StatCounter. Блокировку на Android в любом случае придётся писать заново.

### 11.2 Минимальная версия iOS 18

**Почему:**

- повысить минимальную версию потом дёшево, понизить дорого;
- в июне 2026 iOS 18 стояла на 11% iPhone последних четырёх лет, по данным Apple;
- iPhone 15 владельца на iOS 18;
- все ключевые технологии доступны: Family Controls, DeviceActivity, ManagedSettings, ActivityKit, Vision, `@Observable`.

**Цена:**

- **Два визуальных стиля.** При сборке в Xcode 27 на iOS 26 и новее Liquid Glass обязателен: флаг отказа игнорируется, это подтверждено на форуме Apple. На iOS 18 тот же экран выглядит по-старому.
- **Проверки доступности API.**
- **Две среды симулятора**, около 9 ГБ каждая.
- **Покрытие устройством.** Блокировка на iOS 26–27 до появления второго устройства или тестировщиков остаётся без проверки на устройстве.

### 11.3 Модульность

Одна цель приложения и отдельные цели расширений: Live Activity, монитор активности, экран блокировки при необходимости. Плюс один локальный пакет с чистой логикой: расчёт «сегодня», правила сессии, модели.

- Тесты пакета идут на Mac за секунды, без симулятора.
- Запрет импортировать интерфейсные фреймворки в пакет проверяет скрипт.
- Расширения держим минимальными: по отчётам разработчиков, монитору активности доступно около 6 МБ памяти.
- Новый модуль появляется, только когда для него есть вторая причина.

### 11.4 Цикл проверки

**Основа: командные инструменты Apple.** Сборка, тесты, симулятор, снимки экранов, установка на iPhone. Их удобно вызывать через XcodeBuildMCP: его в феврале 2026 купила Sentry, он работает без окна Xcode и, по описаниям, умеет нажимать на экран симулятора. UI-автоматизация у него в бета-статусе. Телеметрию Sentry нужно отключить. Запасной путь: скилл с прямыми командами `xcodebuild`, `simctl`, `devicectl`.

**Xcode MCP: дополнение для превью и поиска по документации.**

- Apple требует открыть проект в Xcode и показывает уведомление при подключении агента.
- Сторонние источники сообщают о запросе разрешения на каждое новое подключение.
- Фоновый режим упоминается только в бета-сборках.

**Интерфейс проверяется детерминированно.** UI-тесты и снимки экранов. Ручное «тыканье» агента в симулятор оставлено для исследования.

### 11.5 Что агентской системе нужно от среды

Без Mac система проверяет только текст: спецификации, брифы и диффы глазами ревьюера. Выполнить и проверить код она может только там, где есть Xcode. Поэтому от среды системе нужно следующее.

- **macOS и последняя стабильная Xcode.** На них работают скрипт `check`, хуки линтера, тесты, сквозные замеры и вертикальный срез.
- **Симуляторы iOS 18 и актуальной версии.** На них делаются снимки экранов для приёмки владельцем, в том числе для двух визуальных стилей.
- **iPhone только для проверок, которые возможны лишь на устройстве:** Family Controls, датчики, поведение Live Activity на экране блокировки. Агент сам ставит сборку, если телефон разблокирован и в той же сети, и присылает чеклист проверки.
- **Права Claude Code** в `.claude/settings.json`: автоматический режим, заранее разрешённые команды сборки и тестов, запрет push в `main`. Совместимость песочницы Claude Code с инструментами Xcode в документации не описана, её проверяем на опыте с инструментами.
- **Связь с владельцем:** Remote Control и push-уведомления, раздел 8.5.
- **Где живёт система:** только в репозитории. Глобальный фреймворк на этот Mac для работы над Slumpy не ставится, раздел 8.1.

Что агент проверяет сам, а где нужны устройство, владелец или Apple:

| Проверка | Агент сам на Mac | Нужны iPhone и владелец | Нужна Apple |
|---|---|---|---|
| Сборка, логика, UI-тесты, снимки экранов | Да | | |
| Вид Live Activity и Dynamic Island | Да, в симуляторе | Обновления на экране блокировки со временем | |
| Тёмная тема, крупный шрифт, метки VoiceOver | Да | Итоговая проверка VoiceOver | |

### 11.6 Claude Design

- **Что умеет.** Claude Design выдаёт веб-макеты и дизайн-систему, экспортирует в HTML, PDF и PPTX. В Claude Code переносится через `/design-sync`, есть команда `/design`.
- **Чего не умеет.** SwiftUI не генерирует. Liquid Glass в HTML не изображается.
- **Сроки.** Отдельный сайт claude.ai/design работает до 14.12.2026, дальше Claude Design доступен внутри Claude.
- **Порядок работы.** В дизайн-системе сразу задаются ограничения iOS: системный шрифт, шкала Dynamic Type, минимальный размер нажимаемых элементов, светлая и тёмная тема. Агент переносит цвета, шрифты и компоненты в код.
- **Приёмка.** Владелец утверждает снимки экранов из симулятора на iOS 18 и на актуальной версии. Исходный HTML не утверждается.
- **Замена.** Это заменяет веб-скиллы вёрстки.
- **Персонаж.** Анимацию Slumpy Claude Design не делает. Простое лицо из двух точек и линии можно рисовать и анимировать средствами SwiftUI без Rive и аниматора. Проверить прототипом перед функцией персонажа.

### 11.7 Проверка блокировки

Цель: рано подтвердить реализуемость и найти архитектурные ограничения. Что проверяем:

- авторизация Family Controls для себя;
- блокировка одного приложения;
- старт и остановка мониторинга DeviceActivity;
- память расширения;
- поведение при отказе в разрешении.

Нужен платный аккаунт: development capability Family Controls доступна только участникам Apple Developer Program, по таблице возможностей Apple. И нужен iPhone: в симуляторе блокировка не проверяется. Включение блокировки в MVP решается отдельно, по результатам проверки.

## 12. Решения: сейчас, рабочие допущения, позже

**Для ADR-0001, если стек SwiftUI:**

- SwiftUI, минимальная версия iOS 18, последняя стабильная Xcode, Swift 6 strict;
- одна цель приложения, отдельные цели расширений, один локальный пакет, App Group с первого дня;
- цикл проверки на командных инструментах Apple, Xcode Cloud;
- правила данных:
  - всё работает на устройстве без сети;
  - идентификаторы создаются на телефоне;
  - время каждой сессии хранится вместе с её часовым поясом;
  - отнесение минут к дню задаётся явным правилом и закрывается тестами. Само правило продуктовое и его утверждает владелец: например, считать ли сессию через полночь вчерашней и как вести себя при смене часового пояса в поездке;
- каталог строк с первого экрана, язык пока только русский;
- Dynamic Type, VoiceOver и тёмная тема с первого экрана;
- новая сторонняя библиотека добавляется только через ADR.

**Рабочие допущения:**

- бэкенда нет до социальных функций, личное чтение работает без аккаунта;
- аналитики нет до первой сборки для тестировщиков;
- бюджет: план уровня Max, одна сессия агента;
